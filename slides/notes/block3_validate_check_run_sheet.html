Block 3
Segment 4 of 8, and the payoff for the whole workshop. A define.xml that "looks right" can be broken in ways that surface weeks later - at a gateway, in a downstream tool, in a reviewer's browser. Validation-first catches them at the moment they're introduced.
2/6
Four layers, four failure classes
Spend real time here - this is the most valuable slide in the workshop. Layer by layer, say what each one sees that the others are blind to. To XSD an OID is just a string, so it cannot check layer 2. Layer 3 works on objects you haven't serialized yet, which XSD structurally cannot do. In the exercise you meet one file that passes the object checks and fails only XSD, and another that does exactly the reverse.
3/6
Your default call
Filter by exception type - OdmlibOIDError, OdmlibConformanceError, OdmlibElementOrderError - to group a report. Before 0.2.1 this stopped after a few errors, so you fixed one, re-ran, found the next. Now you fix in bulk.
4/6
What validate() misses: XSD
This is the single most common misconception about odmlib validation - people run validate(), see an empty list, and assume schema-valid. Say it plainly: validate() plus validate_file(), every time.
5/6
The repair loop
Note the order inside the loop: fix dangling references BEFORE hunting orphans, because unreferenced_oids() verifies references first and raises while any remain. That ordering is the workflow, not a quirk. In ~20 lines the exercise builds the essence of a Define-XML repair tool.
